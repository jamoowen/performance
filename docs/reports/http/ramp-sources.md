## SQLite implementations and statement reuse

Go's standard `database/sql` package defines the database API; it does not include a SQLite driver. `modernc.org/sqlite` registers a driver called `sqlite` backed by a cgo-free translation of SQLite. It permits a `CGO_ENABLED=0` build and works through `sql.Open("sqlite", ...)`. This removes the cgo requirement; it does not establish a performance improvement over native SQLite. Keep native/translated SQLite versions visible in results. [Standard SQL API](https://pkg.go.dev/database/sql), [modernc driver](https://pkg.go.dev/modernc.org/sqlite@v1.60.1).

Node 24 includes `node:sqlite` without the old experimental flag. In 24.21.0 the module is marked **stability 1.2, release candidate**, not fully stable. `DatabaseSync` and `StatementSync` execute synchronously; retain handles returned by `database.prepare()` for repeated parameterized requests. This choice exposes synchronous database execution on Node's event loop. Its defaults include foreign-key enforcement, defensive mode, and a zero busy timeout, so configure and record values rather than assuming they match other drivers. [Node 24 SQLite API](https://nodejs.org/download/release/v24.21.0/docs/api/sqlite.html).

Bun's `db.query()` caches prepared SQL statements, not query results; `db.prepare()` returns an uncached statement that can also be retained. Bound values can differ on successive executions. Bun supplies synchronous `bun:sqlite`; on Linux it links its own SQLite build, while macOS uses the system implementation. Local and container SQLite versions therefore need separate verification. [Bun SQLite documentation](https://bun.com/docs/runtime/sqlite).

Rusqlite's `Connection::prepare_cached()` reuses an available prepared statement; dropping the returned `CachedStatement` returns it to the cache. In 0.40.2 the API is guarded by the `cache` feature. Explicitly select `features = ["bundled", "cache"]` when using this pin, and set a cache capacity large enough for the fixed SQL statements. The synchronous connection API still needs the shared owner's concurrency discipline. [Rusqlite connection API](https://docs.rs/rusqlite/0.40.2/rusqlite/struct.Connection.html#method.prepare_cached).

Python's standard `sqlite3` connection defaults to an internal cache of 128 prepared statements. `check_same_thread=False` permits cross-thread use but does not serialize a whole application transaction. Connections default to legacy transaction control; set transaction semantics explicitly. FastAPI's synchronous `def` handlers run in a thread pool, which is appropriate for blocking SQLite work; an `async def` handler directly calling blocking SQL can block the event loop. [Python SQLite API](https://docs.python.org/3.14/library/sqlite3.html), [FastAPI concurrency guide](https://fastapi.tiangolo.com/async/).

Exqlite does **not** cache prepared statements automatically. Its direct `Exqlite.Sqlite3` API exposes `prepare`, `bind`, `step`/`fetch_all`, `reset`, and `release`, so an owning process can retain prepared handles and serialize their use. Statements are mutable and must not be manipulated concurrently. Native work runs on dirty NIF schedulers. Release handles when the owning process shuts down; distinguish statement reuse from result caching. [Exqlite README](https://hexdocs.pm/exqlite/readme.html), [direct SQLite API](https://hexdocs.pm/exqlite/Exqlite.Sqlite3.html).

## Framework startup and execution controls

Go net/http is part of the pinned Go runtime; Chi integrates with net/http. Fiber uses fasthttp and has its own context/lifetime rules. Its v3 prefork switch is on `fiber.ListenConfig.EnablePrefork`, rather than the older v2 application option. An ordinary single-process Fiber start should leave prefork off; do not retain borrowed context values after their documented lifetime. [Chi](https://github.com/go-chi/chi), [Fiber configuration](https://docs.gofiber.io/api/fiber/), [Fiber v3 prefork](https://docs.gofiber.io/blog/fiber-v3-prefork-mode/).

Express and Nest should run with `NODE_ENV=production`. A compiled Nest application starts with `node dist/main.js`, without development watches or compilation during measurement. Nest normally uses its Express adapter; this is the selected Nest variant, not a fourth standalone HTTP server. Its application logger can be configured with `logger: false` or selected severity levels. Fastify request logging is optional and can be disabled at construction. Node process clustering is an explicit separate choice, not a consequence of using these frameworks. [Express production guide](https://expressjs.com/en/advanced/best-practice-performance/), [Nest deployment](https://docs.nestjs.com/deployment), [Nest logger](https://docs.nestjs.com/application/logger), [Fastify logging](https://fastify.dev/docs/latest/Reference/Logging/), [Node cluster API](https://nodejs.org/download/release/v24.21.0/docs/api/cluster.html).

Hono documents Bun startup by serving `app.fetch`; Elysia documents a Bun application with `.listen(...)`. Both operate on Bun's server integration, while the native variant uses `Bun.serve`. Worker processes and hot reload are runtime/startup configuration choices; retain a normal production start for the selected process count. [Hono on Bun](https://hono.dev/docs/getting-started/bun), [Elysia quick start](https://elysiajs.com/quick-start), [Bun server](https://bun.com/docs/runtime/http/server).

Axum uses Tokio and Hyper; Tokio's multi-thread builder exposes `worker_threads`, separate from `max_blocking_threads`. Actix Web exposes `HttpServer::workers`, and its application factory can be called once per worker/listener. Rocket exposes `workers`, `max_blocking`, and `log_level`; its release profile defaults to less logging than its debug profile. Worker counts describe different execution machinery, so record them with their meanings. Compile Rust servers in release mode. [Axum](https://docs.rs/axum/0.8.9/axum/), [Tokio builder](https://docs.rs/tokio/latest/tokio/runtime/struct.Builder.html), [Actix HTTP server](https://docs.rs/actix-web/latest/actix_web/struct.HttpServer.html), [Rocket configuration](https://api.rocket.rs/v0.5/rocket/struct.Config.html).

Uvicorn exposes `--workers`, `--no-access-log`, `--loop`, and `--http`; it should not run with `--reload` during measurement. Optional packages alter what the `auto` loop/protocol choices select, so lock and record those too. FastAPI's worker count refers to processes, while synchronous routes additionally use a thread pool. [Uvicorn settings](https://uvicorn.dev/settings/), [FastAPI workers](https://fastapi.tiangolo.com/deployment/server-workers/).

Phoenix is the full Elixir web framework in the matrix. Plug.Router is a lighter routing baseline, not a second full framework or a claim of equivalent popularity. Bandit serves both Plug and Phoenix; Phoenix's endpoint uses `Bandit.PhoenixAdapter` explicitly, while a Plug application can supervise `{Bandit, plug: Router}`. Build with `MIX_ENV=prod` and package a Mix release; ensure the Phoenix endpoint has `server: true`, with code reloading and debug errors disabled. [Plug Router](https://hexdocs.pm/plug/Plug.Router.html), [Bandit integration](https://hexdocs.pm/bandit/Bandit.html), [Phoenix endpoint](https://hexdocs.pm/phoenix/Phoenix.Endpoint.html), [Mix releases](https://hexdocs.pm/mix/Mix.Tasks.Release.html).

The BEAM has normal schedulers, dirty CPU schedulers, and dirty I/O schedulers. Erlang `+S` controls normal schedulers; it does not on its own limit dirty schedulers used by Exqlite. Record the effective scheduler configuration instead of interpreting a single number as total OS threads. Bandit's compression and startup logging are configurable. Build and runtime container environments must remain compatible with the Exqlite native library and the release's Erlang runtime. [Erlang runtime flags](https://www.erlang.org/doc/apps/erts/erl_cmd.html), [Bandit options](https://hexdocs.pm/bandit/Bandit.html), [Mix release compatibility](https://hexdocs.pm/mix/Mix.Tasks.Release.html).
