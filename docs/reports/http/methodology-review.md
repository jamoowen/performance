# Independent HTTP benchmark methodology review

Reviewed 2 October 2026, against source commit `7919b3d84d4e6575f949b6f7c20031f878d8e05d`. This is a read-only audit of the implementations, harness, reports, and retained measurements; no servers were changed and no performance tests were rerun. Source citations below are fixed to that commit. Raw records referenced by run ID remain under the local, ignored `results/http/followups/` directory.

## Verdict

The suite is useful exploratory testing of three concrete API stacks under Kubernetes quotas. The workload, response contract, resource allowances, and generator are substantially aligned. HTTP totals and the percentile/CPU calculations I checked are sound. It is not a controlled ranking of the programming languages, a router microbenchmark, a measurement of maximum capacity, or an explanation of every latency difference.

The strongest result is the six-run, alternating Go scheduling experiment. The largest obstacle to broader interpretation is that apparently identical code sometimes changes client p95 by approximately tenfold while unrelated endpoints move together. Library and implementation differences are also material. Preserve these measurements, qualify conclusions, and investigate those differences before collecting another large matrix.

## What I checked directly

I read the three API implementations, Dockerfiles, contract checks, load script, recording/collection/normalization code, grouping code, and suite publisher. I inspected all 55 retained `result.json` records, metadata, compact HTTP histories, source-timestamped resource samples, and selected original k6 summaries/logs. For Bun Elysia repetition three I also read the original gzipped metric stream: its first five-second window contains 2,931 HTTP durations, all status 200, and p95 8.324 ms, matching the compact history.

The independent record inventory agrees with the published totals: 54 measured attempts, 52 passing, two failing only the zero-drop threshold, and one pre-traffic setup failure. All 54 compact histories are complete and their request, drop, HTTP-failure, and validation-failure totals agree with the original normalized summaries. There are 5,615,056 measured requests, 992 unsent iterations, 129 HTTP failures, no pod restarts, and no collector warnings. Warmups all exited successfully. This verifies recorded consistency; it does not establish that every server-side write was durable or every computed response was correct under load.

Good controls include a single active pod, fresh pod identities, fixed image digests, identical load hash/generator, separate warmup, equal resource allowances, retained failures, and disabled baseline diagnostics. Open-loop arrival-rate traffic with one request per iteration is appropriate for testing fixed offered load. [Load and checks](https://github.com/jamoowen/performance/blob/7919b3d84d4e6575f949b6f7c20031f878d8e05d/benchmarks/http/load.js#L103).

## Findings ordered by impact

### 1. High impact: latency variation is not isolated to application execution

The reported latency measures the HTTP sending/waiting/receiving interval observed by k6. It excludes initial connection/DNS timing and includes network transit and server queuing. Its timestamp is completion time. Those definitions make the five-second graphs correct as completion-window percentiles, but they are not server handler execution time or percentiles of scheduled-but-unsent work. [Official k6 metric definitions](https://grafana.com/docs/k6/latest/using-k6/metrics/reference/), [history implementation](https://github.com/jamoowen/performance/blob/7919b3d84d4e6575f949b6f7c20031f878d8e05d/benchmarks/http/measure/http_history.py#L116).

Concrete evidence: Bun Elysia at 600 RPS has run p95s 77.810, 77.970, and 7.603 ms. In its first run, endpoint p95s all fall between 76.62 and 78.42 ms; in its third, between 6.78 and 8.07 ms. Corresponding waiting p95s are 77.70 and 7.46 ms, receiving p95s approximately 0.091 ms, and connecting p95s zero. The nine repeated memory-stage 600-RPS runs also give similar tails across their very different endpoints. These facts support a shared waiting component as a hypothesis; waiting includes server queues as well as the network and is not proof of Wi-Fi interference.

The published findings disclose Wi-Fi observed during the campaign, uncontrolled CPU frequency, and background host activity. Raw records do not capture client interface, Wi-Fi conditions, per-request server timing, scheduling delay, or full generator resource history. Consequently no measurement cleanly separates HTTP implementation cost from host/client/network variance. Do not explain a 7 versus 78 ms difference as an Elysia optimization, GC effect, or language property without more evidence. [Published limitations and identical-code example](https://github.com/jamoowen/performance/blob/7919b3d84d4e6575f949b6f7c20031f878d8e05d/docs/reports/http/followup-findings.md#L89).

### 2. High impact for language attribution: equal API results do not imply equal internal work

The SQL schema, queries, WAL/NORMAL settings, single connection, and transaction intent are broadly aligned. However Go prepares and retains SQL statements during startup; Bun retains `db.query()` statements; Rust calls `Connection::prepare` inside list/catalog/events/write commands and calls `query_row` for detail/count. Rust therefore includes SQL preparation work that the other two normally amortize. This is a real implementation fairness gap if the intended question is runtime/driver overhead; it does not invalidate the recorded Rust API behavior. Its size is unmeasured. [Go preparation](https://github.com/jamoowen/performance/blob/7919b3d84d4e6575f949b6f7c20031f878d8e05d/benchmarks/http/go/store.go#L76), [Bun preparation](https://github.com/jamoowen/performance/blob/7919b3d84d4e6575f949b6f7c20031f878d8e05d/benchmarks/http/bun/storage.js#L18), [Rust command implementation](https://github.com/jamoowen/performance/blob/7919b3d84d4e6575f949b6f7c20031f878d8e05d/benchmarks/http/rust/src/main.rs#L675). Bun explicitly caches compiled statements, not response/query results. [Official Bun SQLite documentation](https://bun.com/docs/runtime/sqlite#query).

Go uses pool/cgo coordination, Bun synchronous SQLite calls, and Rust a bounded queue plus dedicated SQL thread. Reported SQLite versions differ (3.53.4/3.53.2/3.50.2), as do container libraries (static Alpine/musl Go versus Debian Bun/Rust). These are stack comparisons, not an isolation of language or SQL binding overhead. Fresh runtime/SQLite startup inventories are not recorded for every uninstrumented run. [Go execution](https://github.com/jamoowen/performance/blob/7919b3d84d4e6575f949b6f7c20031f878d8e05d/benchmarks/http/go/store.go#L223), [Rust queue](https://github.com/jamoowen/performance/blob/7919b3d84d4e6575f949b6f7c20031f878d8e05d/benchmarks/http/rust/src/main.rs#L547), [reported versions](https://github.com/jamoowen/performance/blob/7919b3d84d4e6575f949b6f7c20031f878d8e05d/docs/reports/http/followup-findings.md#L23).

Memory algorithms also differ: Go lists collect only the returned page; Bun/Rust collect all matching references, and Rust clones returned products. Rust catalog scans once per category; Go/Bun use one combined scan. Equal results do not imply equal allocations/work. [Go memory](https://github.com/jamoowen/performance/blob/7919b3d84d4e6575f949b6f7c20031f878d8e05d/benchmarks/http/go/memory_store.go#L40), [Bun memory](https://github.com/jamoowen/performance/blob/7919b3d84d4e6575f949b6f7c20031f878d8e05d/benchmarks/http/bun/storage.js#L73), [Rust memory](https://github.com/jamoowen/performance/blob/7919b3d84d4e6575f949b6f7c20031f878d8e05d/benchmarks/http/rust/src/main.rs#L131).

### 3. Medium impact: resource polling has much less resolution than five seconds

The CPU computation is correctly based on distinct source timestamps, identity-checked counter deltas, and time-weighted intervals. CFS touched-period percentage is correctly a delta ratio; it is not percent CPU lost or percent wall time stalled. Sampled working-set maximum is a useful container footprint estimate, not managed heap, exact peak, or memory-pressure measurement. [Resource calculations](https://github.com/jamoowen/performance/blob/7919b3d84d4e6575f949b6f7c20031f878d8e05d/benchmarks/http/measure/results.py#L64), [Kubernetes resource metric definitions](https://kubernetes.io/docs/tasks/debug/debug-cluster/resource-metrics-pipeline/).

Across the 54 raw resource streams I found only **6–9 distinct in-window CPU counter points** per approximately 120-second measurement. Source intervals range from 10.069 to 20.002 seconds, median 15.152 seconds; repeated scrapes return stale points. CPU source age at collector observation ranges from 0.087 to 19.707 seconds, median 7.707 seconds. In-window counter coverage is 69.9–95.4%. The first/last usable counter points can omit approximately 20 seconds at either edge. This is a resolution/coverage limitation, not evidence of a calculation error or large clock skew.

Polling cached cAdvisor faster does not necessarily improve source resolution. “Peak CPU” is a maximum coarse interval average, not an instantaneous peak; low sampled CPU cannot exclude brief saturation. Working set is an estimated container footprint, not managed heap or memory pressure. These are limitations rather than demonstrated arithmetic errors. [Collector](https://github.com/jamoowen/performance/blob/7919b3d84d4e6575f949b6f7c20031f878d8e05d/benchmarks/http/measure/cluster.py#L295).

### 4. Medium impact: high-load failures are valid observations, not capacity ceilings

At 3,000 RPS, Go one-CPU has 451 unsent iterations and Rust two-CPU 541; the latter also has 129 connection-reset HTTP failures (0.036%). An unsent iteration cannot enter the HTTP-duration distribution, while a failed HTTP attempt can. Low latency among sent requests therefore does not mean all offered work was served. HTTP error rate has a sent-request denominator; dropped work is separate. Keep pass rate, drops, achieved throughput, and per-endpoint latency alongside p95. [Normalization](https://github.com/jamoowen/performance/blob/7919b3d84d4e6575f949b6f7c20031f878d8e05d/benchmarks/http/measure/results.py#L23).

Both failed tests dynamically allocated VUs: Go from 1,000 to 1,416; Rust to 1,508. Max iteration duration reached approximately 1.27/1.33 seconds. k6 warns that allocating VUs during a test can consume generator resources and skew results. No continuous generator headroom/lag record isolates allocation versus service degradation. These are legitimate failed attempts, not established server capacity ceilings. [Official VU guidance](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/arrival-rate-vu-allocation/).

### 5. Medium impact: repeats and ordering are enough for exploration, not tight rankings

Scheduling alternates three observations per setting; SQLite/memory rotate runtime order and repeat 600 RPS three times. Frameworks reuse earlier stdlib references; scaling has one attempt per cell and changes CPU quota and worker count together. Framework causal overhead and multicore capacity therefore remain unresolved. [Matrix](https://github.com/jamoowen/performance/blob/7919b3d84d4e6575f949b6f7c20031f878d8e05d/benchmarks/http/measure/campaign.py#L84), [baseline disclosure](https://github.com/jamoowen/performance/blob/7919b3d84d4e6575f949b6f7c20031f878d8e05d/benchmarks/http/measure/suite.py#L33).

Median-of-run-p95 plus min–max is sound descriptive reporting, not pooled percentiles or confidence intervals. Three runs remain three experimental observations despite millions of correlated requests. Healthy-only aggregates are transparent but conditional on passing; keep failed outcomes alongside them when discussing capacity. [Aggregates](https://github.com/jamoowen/performance/blob/7919b3d84d4e6575f949b6f7c20031f878d8e05d/benchmarks/http/measure/compare.py#L370).

Bun's two-worker mode duplicates processes/catalogs and includes a supervisor, whereas Go/Rust share one process. Whole-container metrics correctly include that additional footprint. Scaling is restricted to immutable reads, avoiding shared-state discrepancies. A CPU quota is throughput allowance, not an isolated physical core. [Launcher](https://github.com/jamoowen/performance/blob/7919b3d84d4e6575f949b6f7c20031f878d8e05d/benchmarks/http/bun/launcher.js#L9), [Kubernetes CPU policies](https://kubernetes.io/docs/tasks/administer-cluster/cpu-management-policies/).

### 6. Medium representativeness limitation: traffic is highly repetitive

The mixed load is 35% list, 25% detail, 15% catalog report, 15% quote, 10% event batch. Lists always search books/product with 20 results; quotes always use products 1 and 2; batches always have the same three event types/values. Because operation and ID selection use the same iteration number modulo 20 and 5,000, a complete cycle accesses only 1,250 distinct detail IDs, 500 batch user IDs, and 35 list offsets. The six-operation declaration includes events-report, but mixed intentionally uses only the first five: it does not read stored event totals during measured mixed traffic. This is equally applied and therefore not an asymmetrical cheat, but it is a small, warm, cache-friendly application workload rather than broad production traffic. [Selection and payloads](https://github.com/jamoowen/performance/blob/7919b3d84d4e6575f949b6f7c20031f878d8e05d/benchmarks/http/load.js#L140).

Under-load checks verify response shape, not exact values, result lengths, expected hashes, or final stored totals. Separate contract tests verify many exact results, atomicity, bad inputs, and concurrent writes, which substantially improves confidence; they do not prove correctness of every measured response. Any future optimization that skips work must pass both exact contract checks and an appropriate post-run integrity check. [Load checks](https://github.com/jamoowen/performance/blob/7919b3d84d4e6575f949b6f7c20031f878d8e05d/benchmarks/http/load.js#L216), [exact contracts](https://github.com/jamoowen/performance/blob/7919b3d84d4e6575f949b6f7c20031f878d8e05d/benchmarks/http/tests/contract_test.py#L152).

### 7. Medium future-reporting defect: grouping omits build identity

The compatibility key includes workload, quotas, generator/load hash, node UID/version and runtime knobs, but not image digest, application source commit, or experiment name. I copied a real record in memory, changed those three fields, and obtained the same compatibility key. Loading future runs from different app builds with otherwise equal settings can silently combine them in healthy-run aggregates. The current isolated suite pins one image per applicable implementation/configuration, so I found no current mixed-build aggregate requiring numerical correction. Add build identity within each implementation/variant's repetition group; distinct runtime image digests naturally differ and should not prevent intentional cross-runtime display. [Compatibility key](https://github.com/jamoowen/performance/blob/7919b3d84d4e6575f949b6f7c20031f878d8e05d/benchmarks/http/measure/results.py#L205), [grouping](https://github.com/jamoowen/performance/blob/7919b3d84d4e6575f949b6f7c20031f878d8e05d/benchmarks/http/measure/compare.py#L378).

Raw captures and complete provenance remain local; publishing sanitized summary JSONs and a build/environment manifest would improve external reproducibility without exporting every large capture.

### 8. Low impact documentation mismatch: no explicit overall p95 threshold

The findings state that every run requires both overall and per-operation p95 ≤1,000 ms. `buildThresholds` actually declares per-operation duration thresholds, plus global HTTP/check/drop thresholds, without an explicit overall duration threshold; raw k6 summary `http_req_duration` has no `thresholds` member. Correct that description or deliberately add an overall threshold in the next load-script version. All recorded overall p95s are below 1,000 ms, so this does not change these outcomes. Per-operation targets are useful because a pooled mixed percentile can otherwise hide a slow endpoint. [Actual thresholds](https://github.com/jamoowen/performance/blob/7919b3d84d4e6575f949b6f7c20031f878d8e05d/benchmarks/http/load.js#L69), [current description](https://github.com/jamoowen/performance/blob/7919b3d84d4e6575f949b6f7c20031f878d8e05d/docs/reports/http/followup-findings.md#L32).

The documentation wording was corrected after this review; all recorded results and the audited load script remain unchanged. Build-identity grouping and the other recommendations above are not implemented by this review.

## Interpretation that survives this audit

**Go scheduling:** Median p95 341.3 →53.7 ms and CFS touched periods 74.2% →33.7% under the same one-CPU quota, old image and mixed SQLite workload is strong evidence that this runtime setting mattered in this configuration. A plausible mechanism is a change in scheduling/coordination and bursty quota consumption; it is not a proof that all native SQLite CPU is Go scheduler overhead. `GOMAXPROCS=1` limits simultaneous Go execution, not total process threads or native cgo execution. The contemporary Go default has a floor of two unless visible CPUs/affinity are smaller: the earlier setting of two under one-CPU quota was compatible with the documented default, not simply an app ignoring container limits. [Official runtime documentation](https://pkg.go.dev/runtime#GOMAXPROCS), [quota/parallelism explanation](https://go.dev/blog/container-aware-gomaxprocs).

**Database path, moderate confidence:** Sampled CPU medians at 600 RPS fall Go 838→277m, Bun 493→265m, Rust 611→244m with SQLite replaced by memory. This supports a large database-path cost, with precise percentages limited by cross-stage sampling. It changes SQL execution, conversion, coordination and filesystem work together. Historical native SQLite/cgo attribution does not isolate cgo transition overhead. Memory CPU's near-convergence argues against treating the earlier gap as universal language performance.

**Bun/Rust and frameworks, low causal confidence:** Bun's JavaScriptCore runtime and native SQLite API mean HTTP/SQL work is not all interpreted JS, so matching a compiled Go stack is unsurprising in principle. The data cannot partition native build, binding, HTTP or JIT benefits. Rust's numbers apply to this Axum/Tokio/rusqlite implementation, including its uncached SQL and different algorithms. The approximately 9% framework CPU difference is too confounded by unpaired observations and variance to establish router overhead. [Official Bun overview](https://bun.com/docs), [SQLite API](https://bun.com/docs/runtime/sqlite).

**More cores, low causal confidence:** Go two-CPU consumes >1 CPU and serves the offered rate at 3,000 RPS, but Bun/Rust one-CPU also serve it in their attempts. No consistent tail benefit appears. Most sampled averages are below quota, cells have one attempt, and capacity was not bracketed repeatedly. This does not resolve the large-machine hypothesis; parallelism helps parallel work, adds coordination, and cannot remove serial SQL bottlenecks.

## Smallest useful next steps

1. Correct the threshold description and group repetitions by per-variant build identity. Keep existing results and version future load-script changes explicitly.
2. Calibrate the shared delay first: three alternating Go/Bun pairs at 600 RPS, existing memory mixed load, verified wired route, fully preallocated VUs, continuous generator CPU/RSS/lag, and low-overhead server handler-duration histograms. This six-measurement diagnostic is more useful than repeating all 54 cells.
3. For database attribution, cache Rust statements and separately align SQLite build/options/query plans. Keep instrumented profiles separate from benchmark repeats.
4. After calibration, repeat relevant scaling cells and bracket sustainable throughput against declared endpoint latency/error/drop SLOs. Use paired/randomized repetitions and complete cgroup coverage; show pass rates as well as successful-run latency.

These steps are recommendations, not changes or runs performed by this audit. Existing evidence supports deployment tuning and database-cost hypotheses, but not a universal language winner or a proven explanation for the shared client tails.
